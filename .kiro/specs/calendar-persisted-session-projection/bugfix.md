# Bugfix Requirements Document

## Introduction

The academy must preserve the admin calendar as a pure, read-only projection of persisted `class_sessions`, using the lifecycle `RecurringSchedule → SessionGeneratorService → class_sessions → CalendarQueryService → CalendarEventResource → /admin/calendar/events → FullCalendar`. This bugfix specification also establishes the bounded domain guarantees required for reliable calendar data: immutable business-code allocation, an extensible immutable domain-event stream, deterministic room resolution, conflict-free availability validation, authoritative business rules, and serialized implementation ownership. The scope explicitly excludes capability matching and capability engines, Holiday/Equipment/Vacation/Capacity/Multiple Resources availability rules, and any Force Override behavior. No FullCalendar rewrite, synthetic calendar event, calendar-time session generation, or persisted-session omission is permitted. The required Friday holiday rule remains scheduling/business data, not an additional availability conflict dimension.

The requirements use `C(X)` for the buggy-input predicate, `P(result)` for the required fixed result, `¬C(X)` for non-buggy inputs whose behavior must be preserved, `F` for the original behavior, and `F'` for the fixed behavior. The fix-checking properties are: for every `X` satisfying `C(X)`, `P(F'(X))` holds; every matching persisted session maps one-to-one to one event while preserving its ID and order; every committed business-code allocation is namespace-unique, immutable, permanently retired after allocation, and atomic; every committed supported state change has exactly one immutable ordered event; every room choice follows preferred-room-first then lowest stable room ID; every supported availability conflict rejects atomically for every actor and permission; and every affected business rule and orchestration invariant is tested. The preservation property is `F(X) = F'(X)` for every `X` satisfying `¬C(X)`, except where an explicit expected-behavior clause corrects the defect.

**Correctness properties and testing strategy.** Property and integration tests SHALL generate valid and invalid date ranges, optional filter combinations, persisted-session sets, concurrent code-allocation attempts, transaction failures, idempotency-key replays, room intervals, and availability identities. Calendar tests SHALL assert zero writes and zero `SessionGeneratorService` invocations for empty results, exact count and ordered ID sequence through every boundary, first-mismatch detection, and no downstream reconciliation. Business-code tests SHALL assert the format, independent per-prefix sequence, immutability, retirement, atomic visibility, concurrency/retry outcomes, authorized escaped display, and controlled failure. Event tests SHALL assert the complete envelope and payload facts, exactly-one emission, UTC time, strictly increasing commit-order position, immutable reads, rollback behavior, idempotency behavior, and all listed event types. Room and availability integration tests SHALL assert the exact overlap predicate, deterministic selection, race-safe atomic failure, the three allowed conflict dimensions, and absence of every forbidden override or deferred dimension. Business-rule tests SHALL read `docs/BusinessRules.md`, cover every stated rule, and fail when implementation or tests contradict it. Orchestration tests/checks SHALL assert repository and phase inspection, dependency and exclusive ownership graphs, dependency requests, affected-test gating, and post-merge documentation updates.

## Execution Scope Alignment

The design and task plan in this folder implement only the persisted-session calendar projection repair. The business-code, domain-event, generalized room/availability, business-rule, and orchestration clauses in this requirements document have no matching implementation design or tasks here; they remain deferred and must not be represented as completed by this bugfix checkpoint. They require their own approved design and task plan before execution.

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN an explicitly requested valid inclusive start/end range contains zero persisted `class_sessions` records and recurring schedules exist for dates in that range, including 2026-08-05 when demo schedules exist only on weekdays 1 and 4, THEN the system can attribute the empty result to the event-feed or rendering lifecycle instead of to the absence of persisted source records.
1.2 WHEN a valid inclusive start/end range contains persisted `class_sessions` records and optional `teacher_id`, `student_id`, and/or `room` filters are supplied, THEN the system can omit a record that matches every supplied filter, or include a record that fails one of those supplied filters; `instrument_id` can incorrectly affect membership.
1.3 WHEN a valid inclusive range or any optional calendar filter is absent, malformed, or outside the supported query contract, THEN the system can produce an undefined result rather than a controlled validation response without writes or generation.
1.4 WHEN a persisted `class_sessions` record is processed by the calendar lifecycle, THEN the system can produce zero or more than one JSON or FullCalendar event, or can replace, coerce, or omit its stable `class_sessions.id`, so persisted-session, JSON-event, and normalized/rendered FullCalendar-event counts or IDs can differ.
1.5 WHEN a count or stable-identifier mismatch occurs between consecutive calendar stages, THEN investigation or repair can continue past the first mismatching boundary and later stages can add, remove, replace, or alter events to compensate.
1.6 WHEN a calendar request returns no matching persisted sessions, THEN the system can write rows, invoke `SessionGeneratorService`, or create synthetic, fallback, or replacement events during request processing.
1.7 WHEN a student or teacher is created or assigned a business code, THEN the system can derive the code from `max(id)+1`, an entity ID, a primary key, or a mutable entity attribute, allowing collisions under concurrency or reuse after deletion.
1.8 WHEN concurrent business-code allocations, a failed transaction, or a retry occurs, THEN the system can expose duplicate codes, commit more than one assignment for one logical allocation, release a reserved code, reuse a failed reservation, or leave an allocation and entity assignment partially visible.
1.9 WHEN an allocated business code is displayed, THEN unauthorized output can disclose it or user-controlled code content can be rendered without escaping.
1.10 WHEN a supported Student, Teacher, Enrollment, Class Session, Attendance, Invoice, or phone state change occurs, THEN the system can lack one immutable ordered event containing the required identity, type, actor, UTC time, payload, stream position, and idempotency identity, or record the event independently from the state change.
1.11 WHEN a supported command is retried with the same idempotency key, THEN the system can create a duplicate state change or event; WHEN the same key is reused with different input, THEN the system can mutate state instead of rejecting the request.
1.12 WHEN a domain event is read after commitment, THEN the system can edit, delete, reorder, replace, expose an empty idempotency key, or return a non-commit-ordered stream; rollback can expose state or an orphan event.
1.13 WHEN a student is created, a teacher is assigned or changed, an enrollment is created, a session is cancelled, attendance is recorded, an invoice is paid, or a phone is changed, THEN the system can omit the required event type or omit payload facts sufficient to identify the relevant student, teacher, enrollment, session, attendance, invoice, or phone change.
1.14 WHEN a preferred room is unavailable or absent and rooms are available, THEN room selection can use unspecified ordering or capability matching instead of preferred-room-first and ascending stable room ID.
1.15 WHEN room resolution succeeds but another transaction creates an overlapping session before commit, THEN the system can commit a conflicting session, assignment, or override; WHEN no room is available, it can persist partial state.
1.16 WHEN interval availability is evaluated, THEN endpoint-touching sessions can be treated as overlapping, or unsupported Holiday, Equipment, Vacation, Capacity, or Multiple Resources rules can be applied as availability conflicts.
1.17 WHEN a Teacher Busy, Student Busy, or Room Busy conflict exists, THEN the system can permit a save for an actor or permission through a `force_override` flag, permission, bypass, alternate path, or equivalent behavior, or can return no conflict identity/dimension.
1.18 WHEN business-rule validation is implemented or tested, THEN the system can omit or contradict the authoritative rules for required and unique Student national ID, required and unique Student phone, required Teacher national ID, 30-minute normal sessions, 60-minute makeup sessions, Saturday–Thursday working days, and Friday holiday.
1.19 WHEN `docs/BusinessRules.md` is absent, incomplete, or contradicted by implementation or tests, THEN affected behavior can be implemented without a single source of truth.
1.20 WHEN implementation agents are spawned, THEN the orchestrator can skip full repository and phase inspection, dependency analysis, exclusive file ownership, conflict detection, or dependency-aware task creation, allowing two agents to modify one file or an agent to modify a file it does not own.
1.21 WHEN an agent needs an unauthorized file, or when a phase is merged, THEN it can modify the file without a dependency request, overwrite another owner, or merge while affected tests are absent, skipped, unavailable, failing, or while required decision-log and changelog updates are missing.

### Expected Behavior (Correct)

2.1 WHEN an explicitly requested valid inclusive start/end range contains zero persisted `class_sessions` records, including 2026-08-05 when the database has no rows and demo schedules exist only on weekdays 1 and 4, THEN the system SHALL return an empty JSON event collection.
2.2 WHEN a valid inclusive start/end range contains zero matching persisted `class_sessions` records, THEN the system SHALL perform zero writes, SHALL NOT invoke `SessionGeneratorService`, and SHALL NOT create synthetic, fallback, or replacement events.
2.3 WHEN a valid inclusive start/end range and optional `teacher_id`, `student_id`, and/or `room` filters are supplied, THEN the system SHALL include exactly those persisted `class_sessions` records that match the inclusive range and every supplied filter; an omitted filter SHALL impose no restriction, and `instrument_id` SHALL be ignored for membership.
2.4 WHEN a query input is invalid or outside the supported calendar contract, THEN the system SHALL return a controlled validation response and SHALL perform no write, generation, synthetic-event creation, or downstream reconciliation.
2.5 WHEN a persisted `class_sessions` record is included in the calendar query result, THEN the system SHALL produce exactly one event through `CalendarQueryService`, `CalendarEventResource`, and `/admin/calendar/events`, and SHALL preserve the exact `class_sessions.id` from the query through the resource and endpoint JSON.
2.6 WHEN `/admin/calendar/events` returns one JSON event for an included persisted `class_sessions` record, THEN FullCalendar normalization and rendering SHALL produce exactly one event whose stable identifier equals the JSON event's stable identifier.
2.7 WHEN the calendar lifecycle completes for a valid inclusive range and its optional filters, THEN the system SHALL preserve both count and ordered ID sequence: `count(matching persisted class_sessions) = count(JSON events) = count(normalized/rendered FullCalendar events)`, and each sequence SHALL be identical.
2.8 WHEN a count or stable-ID mismatch is detected between consecutive stages in the order `CalendarQueryService`, `CalendarEventResource`, `/admin/calendar/events`, and FullCalendar normalization/rendering, THEN the system SHALL identify the first mismatching boundary and SHALL NOT reconcile, add, remove, replace, or alter events downstream.
2.9 WHEN a student or teacher receives a business code on approved creation or backfill, THEN the system SHALL allocate one code before scheduling availability, using a backend-owned sequence independent of primary key, entity ID, `max(id)+1`, and mutable attributes; the format SHALL be `STU-` or `TCH-` followed by exactly six decimal digits.
2.10 WHEN a business code is supplied or edited by a user after allocation, THEN the system SHALL reject the edit or preserve the allocated code unchanged; the code SHALL be immutable.
2.11 WHEN business codes are allocated, THEN uniqueness SHALL be guaranteed independently within each prefix namespace (`STU-######` for students and `TCH-######` for teachers); the requirements SHALL NOT impose an unnecessary cross-prefix uniqueness rule, and no committed code SHALL belong to two entities.
2.12 WHEN a code is allocated, its entity is deleted, its transaction rolls back, or its reservation otherwise fails, THEN the code SHALL be permanently reserved/retired and SHALL never be returned, released, or reused; a later allocation SHALL use a never-before-issued code.
2.13 WHEN concurrent business-code allocations or retries target one or more entities, THEN coordination SHALL yield at most one committed assignment per logical entity/command and no duplicate committed code; contention or exhaustion SHALL return a controlled failure, and a failed reservation SHALL remain retired.
2.14 WHEN a business-code allocation and entity assignment are committed, THEN both SHALL become visible atomically; WHEN either cannot commit, THEN neither a partial assignment nor a falsely committed allocation SHALL be observable.
2.15 WHEN an allocated business code is displayed, THEN the system SHALL enforce the applicable authorization and SHALL HTML-escape the rendered value.
2.16 WHEN one supported command/state change commits for a Student, Teacher, Enrollment, Class Session, Attendance, Invoice, or phone value, THEN the system SHALL append exactly one immutable event in the same transaction with a globally unique event identity, supported or future event type, entity type and ID, actor identity or an explicit absent-actor value, UTC event time, a strictly increasing commit-order stream position, relevant payload, and a non-empty idempotency key.
2.17 WHEN the supported changes occur, THEN the event stream SHALL support `Student Created`, `Teacher Assigned`, `Teacher Changed`, `Enrollment Created`, `Session Cancelled`, `Attendance Recorded`, `Invoice Paid`, and `Phone Changed`, respectively; each payload SHALL contain facts sufficient to identify and verify the relevant subject and changed outcome, while future event types SHALL use the same envelope without invalidating existing events.
2.18 WHEN domain events are read, THEN the system SHALL return them in immutable commit order and SHALL never edit, delete, reorder, or replace a committed event.
2.19 WHEN a state-change transaction commits, THEN its exactly-one corresponding event SHALL commit in that same transaction; WHEN the transaction rolls back, THEN neither the state nor its event SHALL be visible.
2.20 WHEN a command is retried with the same non-empty idempotency key and equivalent input, THEN the system SHALL return the original outcome and event without creating another mutation or event; WHEN the same key is used with different input, THEN the system SHALL reject the request without mutation.
2.21 WHEN a session has a preferred room and that room is available for the requested interval, THEN `RoomResolver` SHALL select the preferred room.
2.22 WHEN a preferred room is absent or unavailable and one or more rooms are available, THEN `RoomResolver` SHALL select the first available room by ascending stable room ID; it SHALL perform no capability matching and SHALL invoke no capability engine.
2.23 WHEN interval `[start,end)` is checked against another interval `[other_start,other_end)`, THEN the intervals SHALL overlap if and only if `start < other_end AND end > other_start`; touching endpoints SHALL not overlap.
2.24 WHEN no room is available, THEN the operation SHALL fail atomically with `Room Busy` and SHALL persist neither a session, assignment, nor override; WHEN a race creates a conflict between resolution and commit, THEN the operation SHALL return `Room Busy` and persist nothing.
2.25 WHEN availability is evaluated in this version, THEN the only conflict dimensions SHALL be exactly `Teacher Busy`, `Student Busy`, and `Room Busy`, each based on overlapping persisted sessions and the relevant identity; the result SHALL expose the conflict identity and dimension.
2.26 WHEN Holiday, Equipment, Vacation, Capacity, or Multiple Resources would otherwise be evaluated, THEN the system SHALL defer those dimensions and SHALL not report them as availability conflicts; the required Friday holiday rule SHALL remain scheduling/business data.
2.27 WHEN any supported Teacher Busy, Student Busy, or Room Busy conflict exists, THEN the system SHALL reject the operation for every actor and permission set, preserve prior state, and expose no `force_override` flag, permission, bypass, alternate path, or equivalent behavior.
2.28 WHEN affected behavior is implemented, THEN `docs/BusinessRules.md` SHALL exist before implementation and SHALL be the sole source of truth; it SHALL state that Student national ID is required and unique, Student phone is required and unique, Teacher national ID is required, normal sessions are exactly 30 minutes, makeup sessions are exactly 60 minutes, working days are Saturday through Thursday, and Friday is a holiday.
2.29 WHEN Student, Teacher, Session, or schedule behavior is implemented or tested, THEN code and tests SHALL conform to `docs/BusinessRules.md`; the test suite SHALL cover every stated rule and SHALL fail on any contradiction.
2.30 WHEN the orchestrator prepares implementation agents, THEN it SHALL inspect the entire repository and phase scope, build a dependency graph and exclusive file-ownership graph, detect conflicts, create dependency-aware implementation tasks, finalize one owner per file, and spawn agents only afterward.
2.31 WHEN an agent needs a file it does not own, THEN it SHALL issue a dependency request naming the owner, file, requested change, and reason, SHALL wait, and SHALL not modify, overwrite, or delete that file; the orchestrator SHALL never permit two agents to modify one file.
2.32 WHEN a phase is merged, THEN the orchestrator SHALL first require the complete affected-test set derived from changed files, dependencies, and acceptance criteria to pass; absent, skipped, unavailable, or failing tests SHALL block the merge. After each merge, the documentation agent SHALL update `.kiro/steering/17_DECISION_LOG.md` and SHALL update `CHANGELOG.md` when appropriate; the decision log SHALL include ISO date, phase, decision/reason/status, including `Decision 1: Remove Force Override` with reason `Data Integrity`.

### Unchanged Behavior (Regression Prevention)

3.1 WHEN `SessionGeneratorService` processes an active recurring schedule that requires a future session under the existing schedule-generation rules, THEN the system SHALL CONTINUE TO create that session as a persisted `class_sessions` record before any calendar query can return it.
3.2 WHEN `/admin/calendar/events` receives a valid inclusive date range and valid optional teacher, student, or room filters, THEN the system SHALL CONTINUE to query and serialize only persisted `class_sessions` records that fall within the range and match every supplied filter, while ignoring `instrument_id` for membership.
3.3 WHEN FullCalendar receives valid event data from the calendar endpoint, THEN the system SHALL CONTINUE to normalize and render it without redesigning, replacing, or rewriting FullCalendar, and SHALL preserve existing RTL, accessibility, and responsive behavior.
3.4 WHEN zero persisted `class_sessions` records match a valid inclusive range and its optional filters, THEN the system SHALL CONTINUE to render zero calendar events, with no synthetic fallback.
3.5 WHEN a persisted session is projected, THEN the system SHALL CONTINUE to preserve its `class_sessions.id`, count, and ordered ID sequence through query, resource, endpoint JSON, normalization, and rendering; a first mismatch SHALL remain observable and SHALL not be repaired downstream.
3.6 WHEN a business code is read after assignment, THEN the system SHALL CONTINUE to return the same immutable code for that entity across reads, permitted unrelated updates, retries, and deletion history; unrelated entity attributes and identifiers SHALL remain unchanged.
3.7 WHEN a domain event is read after commitment, THEN the system SHALL CONTINUE to return its original immutable envelope, payload, actor-or-absent value, UTC time, idempotency key, and commit order without changing existing calendar projection behavior.
3.8 WHEN a preferred room is available, THEN the system SHALL CONTINUE to prefer it; when it is unavailable or absent, the system SHALL CONTINUE to select the first available room by ascending stable room ID, without introducing capability matching.
3.9 WHEN no Teacher Busy, Student Busy, or Room Busy conflict exists, THEN the system SHALL CONTINUE to save a valid session using existing persisted-session and transaction behavior; touching interval endpoints SHALL remain available.
3.10 WHEN a business rule is not one of the explicitly required rules in `docs/BusinessRules.md`, THEN the system SHALL CONTINUE to avoid inventing a conflicting rule in this version; deferred availability dimensions SHALL remain deferred and Friday SHALL remain scheduling/business data.
3.11 WHEN an implementation agent owns a file and completes its assigned change, THEN the system SHALL CONTINUE to preserve exclusive ownership, dependency-request waiting, complete affected-test gating, and post-merge decision-log/changelog updates.
