# Implementation Plan: Academy Scheduling and Profiles

## Overview

This plan decomposes the approved additive feature across nine agents, with exclusive file ownership, dependency waves, compatibility gates, MySQL/InnoDB correctness checks, and continuous documentation maintenance. It creates no implementation agents and does not authorize production changes during specification authoring.

## 1. Execution contract

This is the implementation plan for `academy-scheduling-and-profiles`. It is additive and must preserve the existing Laravel modular-monolith boundaries. Every task below is coding-focused, has a stable ID, one of the nine approved owner agents, explicit dependencies, an exclusive target-file group, and requirement/design traceability. The task list is a plan only; no implementation agent is created by this document.

Approved decisions are fixed: persisted `ClassSession` is the only calendar source; dynamic persisted rooms initially contain only `A101`, `A102`, and `A103`; the preference map is Violin→A101, Voice→A102, Piano→A103, Classical Guitar→A102, Pop Guitar→A102; preference is optional and fallback is any compatible available room; Student/Teacher email uniqueness is global; national ID is required for new profiles when the setting is enabled and compatibility-null for legacy/imported records; photos use configurable Storage and Intervention Image GD; no artificial gaps are inserted; sessions are continuous unless a real blocker exists; Timeline and System Activity remain separate; calendar editing uses existing mutation owners; existing routes, APIs, Blade contracts, policies, DTOs, services, and persisted-session behavior remain compatible.

### 1.1 Required completion evidence

- All task IDs are checked only after implementation and focused validation pass.
- A task is incomplete if it changes an unowned file, introduces a duplicate owner, bypasses the Scheduling Domain, synthesizes a calendar event, or omits its requirement references.
- MySQL/InnoDB is the production correctness adapter. SQLite tests may cover fast behavior but must not claim MySQL/InnoDB locking semantics.
- Never run `migrate:fresh`, `db:wipe`, destructive cleanup, or destructive rollback without explicit approval.

## 2. Nine-agent ownership and strict file boundaries

No two agents may edit the same file, migration, route file, service, model, view directory, test directory, or documentation file. Cross-boundary work is performed through a typed contract and hand-off; the receiving owner applies the integration change. Review comments never grant write access.

### 2.1 Conflict rules

1. Before editing, the owner records the exact file list in the hand-off and checks it against this table.
2. A task may not edit another owner’s file “for integration convenience.” It must publish a contract, request a hand-off, and let the owning agent make the edit.
3. Shared concepts are shared through DTOs/interfaces/events, not shared file ownership. The first owner of a canonical contract owns additive changes to that contract.
4. Existing route names and existing public DTO keys are frozen. The Calendar agent owns route-file edits; the owner of a mutation service owns its implementation; the UI agent consumes the resulting contract.
5. Database migrations are append-only and owned only by Database & Domain. Other agents may submit migration requirements but may not create or edit migration files.
6. Tests never change production behavior to make a test pass. Documentation never records an unapproved decision as approved.
7. If ownership becomes ambiguous, stop the affected task, record the conflict in the hand-off, and use the blockers section below; do not fork a second implementation.

## 13. Merge strategy and ordered integration phases

### 13.1 Integration order

1. **Phase A — Baseline and contracts:** merge DB-01, S-01, P-01, H-01, C-01, D-01 after static ownership review. This phase must not change runtime behavior.
2. **Phase B — Additive persistence:** merge DB-02 through DB-04, then DB-03 model/index contracts, with preflight and rollback review. Do not enable strict constraints before DB-01 evidence exists.
3. **Phase C — Domain owners:** merge S-02/S-03, P-02/P-03/P-04, R-01, H-02/H-03, and D-02. Each branch must use the shared contracts and must not copy business logic.
4. **Phase D — Mutation and recurrence:** merge S-04/S-05, R-02/R-03, H-04, P-05, and DB-05/DB-06. Final persistence must lock/re-read/evaluate/audit in one transaction.
5. **Phase E — Calendar and UI:** merge C-02/C-03, then UI-01 through UI-04, then D-03. Calendar feed compatibility is checked before browser integration; UI never becomes a new mutation owner.
6. **Phase F — Verification:** merge T-01 through T-06, D-04/D-05, then T-07 evidence. Only this phase may mark the feature complete.

### 13.2 Branch and hand-off rules

- Each agent works in an isolated branch or worktree named for its task IDs and submits a manifest of changed files. The manifest must contain no path outside its ownership table.
- Integration is fast-forward/ordered where possible; conflicts are resolved by the owning agent, never by an integrator editing both sides.
- A merge is rejected if it adds a second route for an existing mutation, a calendar event source, browser conflict calculation, controller business logic, Blade query, raw path, unbounded recurrence, or unreviewed constraint.
- After each phase, run only the applicable focused checks; do not use destructive database reset commands. Full tests remain a final checkpoint task, not an excuse to skip phase gates.
- Rollback disables new writes/flags first, retains adapters, restores old owner wiring, and never drops legacy columns, routes, audit records, referenced media, or persisted-session calendar behavior.

## 15. Known blockers and ambiguities (do not invent decisions)

1. **Canonical documentation path is unspecified.** Requirements and design require `Architecture.md`, `BusinessRules.md`, `Database.md`, `API.md`, `History.md`, `CHANGELOG.md`, and `DecisionLog.md`, but neither document states whether they belong under `docs/`, `resources/design/`, the repository root, or another existing documentation location. Tasks use the provisional, non-existing path `docs/academy-scheduling-and-profiles/`. Documentation implementation must stop at D-01/D-05 until the repository owner confirms the canonical path; do not create duplicate copies.
2. **Dynamic-room CRUD versus fixed initial identity scope.** Requirements R2.4 says an authorized administrator may create/update/deactivate/reactivate rooms, while design D5.1 says arbitrary new room identity expansion is outside this feature and “create” means restoring/creating only approved A101/A102/A103 identities. The approved initial seed and no-Room104 decision are preserved. The product owner must clarify whether post-rollout creation of a fourth identity is allowed; until then, implement mutation validation for existing approved identities only and leave expansion blocked.
3. **Global email uniqueness representation.** Requirements explicitly require global uniqueness across Student and Teacher. Design D10.1 describes a `(kind, canonical_value)` claim key, which is correct only if email claims share one global kind rather than separate Student/Teacher kinds. Profile and Database agents must use one shared email namespace and record the exact constraint shape in Database.md; no per-model-only email uniqueness is acceptable.
4. **`national_id_required` activation timing.** The approved rule is required for new profiles when the setting is enabled and nullable/flagged only for legacy/imported records. The rollout must not enable the setting until the identity-health preflight and backfill report pass; any different activation policy requires a superseding decision.
5. **Exact existing file names for some proposed new boundaries.** The design names conceptual classes such as `SchedulingDomain`, `ProfileMediaBoundary`, `SystemActivityService`, and `MutationAuditBoundary`, while the repository currently has adjacent services rather than every class. Owners may choose exact new class names only within their exclusive path and must record the canonical name in Architecture.md before dependent tasks merge; they must not create parallel owners.
